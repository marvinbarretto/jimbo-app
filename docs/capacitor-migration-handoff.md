## Where we are

**Goal:** consolidate jimbo-app (Kotlin telemetry shell) and the gym Next.js PWA into one Capacitor-based Android app. PWA stays the UI canon; jimbo's Kotlin code (collectors, syncers, HC bridge) becomes Capacitor plugins running alongside the WebView.

**Reference architecture:** [localshout-next](../../localshout-next/) — Capacitor wrapping a remote Next.js URL with custom `AppShellPlugin` / `TabBarPlugin` / `BridgeRegistry`. Worth re-reading `MainActivity.java`, `AppShellPlugin.java`, and `definitions.ts` before starting. Key difference from us: localshout has zero WorkManager / receivers; we have a lot.

Why this order: it's the load-bearing background path, has no PWA-facing surface (no plugin needed yet), and lets you verify the Capacitor shell can keep telemetry alive with the WebView closed. Once it works, every later port has a working foundation to layer onto.

## Gotchas

- **`fallbackToDestructiveMigration(dropAllTables = true)`** in `StepsDatabase`. Bumping Room version after the Capacitor port wipes `gym_session_pushes` and the next bridge scan will re-POST 24h of HC sessions as duplicates (no server-side dedup yet). Real fix is server-side: add `hc_uid TEXT UNIQUE` to `gym_sessions`. Defer; just know.
- **Hardcoded gym exercise IDs** in `GymSessionBridge.kt:23-26` (`ex_6fea39d8` etc.). These are `source: 'user'` rows seeded by my curl calls on 2026-05-22 against the live API. If the gym DB is reseeded or restored, the bridge silently 4xx's. Better long-term: probe by name on first run and cache, or seed as `source: 'system'` via SQL migration.
- **Smoke-test session `ses_7569e62e`** still in jimbo-api Postgres. No DELETE endpoint exists. Clean via psql when next on the VPS, or add `DELETE /gym/sessions/:id`.
- **Capacitor "Cannot read properties of undefined (reading 'triggerEvent')"** appears once on first launch. Benign — Capacitor JS bridge timing during initial page load. Don't chase it.
- **PWA already has its own bottom tab bar.** If we later add a native TabBar plugin (localshout-style), decide who owns navigation. Probably keep PWA-driven navigation and skip native tabs.
- **Pinning the gym PWA target.** `server.url` defaults to `https://gym-kohl-theta.vercel.app` (rolling latest). Use `CAP_SERVER_URL=<specific-deployment-url> npx cap sync android` to pin to a deployment during native rollouts so we don't chase a moving target. Pattern lifted from localshout's `capacitor.config.ts`.
- **Two APKs installed simultaneously during the port.** Force-stop the legacy one before testing the `.cap` build, or both will run collectors and write to two separate `jimbo_db` Room files. Telemetry will get double-counted server-side (events are deduped by `client_event_id` so it's not catastrophic, but logs get noisy).
- **`NotificationListenerService` (legacy app)** is bound by Android only after the user grants notification access in system settings. After cutover (different applicationId), the user will need to re-grant. Plan a one-time onboarding flow.

## Open architectural questions

These are real forks; don't decide silently:

1. **Plugin granularity.** One `JimboBridge` plugin exposing everything, or several (`HealthConnect`, `Telemetry`, `Activity`, `Haptics`)? localshout split by domain — easier to version independently. Probably do the same, but each split adds boilerplate.
2. **TypeScript plugin definitions — where?** Options: (a) `jimbo-app/plugins/<name>/definitions.ts` like localshout, (b) inside the gym repo (gym is the consumer), (c) tiny npm package. Localshout chose (a). Gym repo would need to `npm install` from a local path or git URL.
3. **BridgeRegistry capability versions.** Mirror localshout's pattern (`registry.registerCapability("telemetry", 1)`)? Worth it for graceful PWA degradation in non-native contexts.
4. **Status / Settings screens.** Legacy Compose `StatusScreen` and `SettingsScreen` show pending events, dead-letter queue, collector toggles, sync constraints. After cutover, either: (a) gym PWA absorbs these as new pages (calls Capacitor plugins for data), (b) drop them (most data is also queryable via dashboard), (c) keep one minimal native screen behind a hidden gesture. Worth a quick decision before the port commits to a direction.
5. **Loading overlay state machine** (localshout `LoadingOverlayManager`). Genuinely improves first-launch perception when the PWA takes 2-3s to load over flaky network. Probably worth porting verbatim — it's self-contained and adds polish that pays for itself.
